# Acceptance matrix — Unicorn 1.0.0-rc.1

This report maps the **Unicorn master development brief** supplied on 22 October 2026 to the current source, automated tests, and remaining acceptance work. Section numbers refer to that brief. Row IDs are stable so a release report can cite individual requirements.

**The candidate is not fully accepted as production v1.0.0.** Code being present and a test being written are separate from that test passing on the target platform.

## Evidence recorded at this snapshot

- **Unit checks:** the reviewed JUnit report records **314 tests, 0 failures, 0 errors**, including 26 controller tests, 27 provider tests, 18 validator tests and 22 storage tests. These include mocks at native boundaries; they do not prove Chromium or Windows behavior.
- **Native Windows verification:** **pending**. The committed Playwright suites and Windows packaging/smoke jobs are described below, but no row treats their existence as a Windows pass. The release report must add the exact commit, Actions run, report artifacts, and any failures or skips after execution.
- **Limited local diagnostic:** a short Linux/Xvfb diagnostic exercised real Chromium navigation, JavaScript/Fetch, native view positioning, device metrics, UI-created jobs, and theme persistence. Its temporary root-only launcher used `--no-sandbox`; it is **not** sandbox, Windows, release-package, or long-duration acceptance evidence.
- **Broader acceptance:** the 24-hour soak, consumer Windows 10/11 reference benchmarks, and independent packet-level DNS/WebRTC audit remain **unperformed**.

See [testing and evidence interpretation](testing.md), [performance acceptance](performance.md), [security boundaries](security.md), and the [user guide](user-guide.md). Attach exact CI evidence here before promoting any pending gate; do not infer a successful installer, a production release, or public-proxy reliability from source checks.

### Reading the matrix

**Implemented** means the described code path exists. **Partial** means a material part of the brief is missing or narrowed. **Not implemented** names absent functionality. **Unit pass** refers to the recorded source test run. **Native pending** refers to committed real-Electron tests awaiting accepted Windows results. **Review only** means source inspection without a dedicated successful behavioral test. Limitations remain applicable even after a native test passes.

## Failure coverage that still needs acceptance evidence

The native suite contains scenarios for unavailable/slow/wrong-country/dropped proxies, untrusted certificates, unsafe URLs, unapproved redirects/popups, page timeouts, HTTP restrictions, known challenges, cancellation, pause/resume, renderer crash/manual reopen, and profile restart. Endpoint duplicates, allocation races, queue removal during a run, interrupted saved jobs, malformed provider data and corrupt state are additionally covered at unit level. Their evidence level must remain explicit when reporting the original failure checklist.

Dedicated end-to-end provider API timeout/malformed-response recovery, OS network disconnect/reconnect, a missing-internal-link page, successful approved-external-stage completion, a successful bounded replacement-proxy retry, and process interruption during a live scheduled run are not all represented by completed native acceptance tests. The existing fixture tests must first pass on Windows; these additional coverage gaps must then be resolved or explicitly accepted as release-candidate limitations.

## Promotion gates

Before marking mandatory acceptance complete, attach the exact source commit and passing native Windows reports; verify installer, portable archive, installed executable and published checksums/URLs; record consumer Windows 10/11 performance against a stated reference workload; complete the 24-hour soak and packet-level DNS/WebRTC audit; and either implement or explicitly resolve each **Partial** requirement above. Report skipped or failed tests alongside successful checks.

External dependencies include live public proxy supply, the diagnostic service, consumer test hardware, sustained test infrastructure, and a signing certificate if signed delivery is required. These dependencies do not excuse reporting unperformed work as passed. The optional backends in A40 do not become mandatory merely because they are listed.
